MC68000 specifications and complete opcode-word coverage
=======================================================

The original CPU implementation is repaired in place, with independent checks
for both decoders. All 84 original instruction-test groups have real executable
specifications. The 67 unasserted templates are not placeholder passes. Existing
C++ assertions, the original PDF design guide, 28 JSON examples, pinned MAME
vectors and an optional pinned differential oracle remain complementary layers.

Every opcode word having a test does not prove all operand values, timing states
or console behavior. Readable specifications and independently supplied expected
results determine correctness; a baseline of existing failures does not.

Offline strict checks
---------------------

    cmake -S UnitTests -B build/cpu -DCMAKE_BUILD_TYPE=Debug
    cmake --build build/cpu --config Debug --parallel 2
    ctest --test-dir build/cpu -C Debug --output-on-failure
    python UnitTests/conformance/complete.py --worker build/cpu/vector_worker --specifications-only --report-dir build/specifications-report

The suite currently contains 8,155 instruction cases plus 42 sequences: 8,197 per
decoder, 16,394 evaluations across both paths. Expectations use width-limited
Python arithmetic and documented hardware behavior, never captured CPU outputs.
They cover:

* Byte/word/long arithmetic, carry/borrow/overflow, upper-register preservation,
  address-register sign extension, extend/sticky-Z and signed/unsigned multiply
  and quotient/remainder boundaries, including INT_MIN/-1.
* Shift/rotate counts 0..63, both incoming X states, all widths and directions,
  memory word forms, dynamic bit numbers 0..63 and immediate bit numbers 0..255.
* All 32 CCR combinations for Bcc/Scc/DBcc, terminal counters, BRA/BSR, JSR/RTS,
  LINK/UNLK and MOVEM ordering, including the base register and A7 edge cases.
* Legal MC68000 addressing modes, signed displacement/index values, Dn/An indexes,
  PC-relative and absolute addresses, ignored later-CPU scale bits, immediate
  operands and A7 byte alignment.
* SR/CCR masks, privilege exceptions, immediate USP/SSP switching, MOVEP, BCD,
  TAS, both TRAPV outcomes, TRAP vectors, illegal encodings and line-A/F traps.
* Interrupt masking/priority, STOP wakeup, trace boundaries, reset vectors and
  external RESET callback delivery. Sequences test stack frames and prefetch
  effects, including modifying the next instruction through extension-word EAs.
* Odd word/long accesses and odd control targets, seven-word address-error
  frames, staged An/flag updates, partial long transfers and exact fault-stage
  timing. Focused guards cover CLR and MOVE SR destination dummy reads, CHK trap
  paths, LINK A7 and odd JMP/JSR displacement targets.

Only hardware-undefined bits are omitted. The address-error special status word
has 11 undefined high bits; its five defined direction/function-code bits remain
checked. Some broad readable address-error cases allow the manual's variable
saved-PC pipeline position; targeted guards and independent MAME vectors assert
exact saved PC, fault address, IR and cycles. Reset masks undefined Dn/An/USP.

Seven CTest targets execute the original regressions, adapter checks, handwritten
cases and complete specifications. The normal and sanitizer profiles both run
strictly, without --baseline arguments. Historical .json/.json.gz snapshots are
retained for audit history and do not define acceptance criteria. Wrong results
and crashes remain failures. --mode audit only changes the diagnostic command's
exit policy; it never marks a failing case as passing. Adapter/input errors exit 2.

Independent complete decode sweep
--------------------------------

    python UnitTests/conformance/prepare_reference.py
    python UnitTests/conformance/fetch.py
    cmake -S UnitTests -B build/cpu-reference -DCMAKE_BUILD_TYPE=Debug -DDRIVONIX_REFERENCE_DIR="ABSOLUTE_REPO_PATH/build/conformance-data/reference"
    cmake --build build/cpu-reference --config Debug --parallel 2
    python UnitTests/conformance/complete.py --worker build/cpu-reference/vector_worker --oracle build/cpu-reference/reference_worker --report-dir build/complete-cpu-report

Substitute the actual absolute checkout path in the configure command. A Windows
multi-configuration Debug build uses Debug/vector_worker.exe and
Debug/reference_worker.exe. The optional oracle also requires a C compiler.

The default command uses eight deterministic operand/extension/status patterns
for all 65,536 words: 524,288 differential inputs plus the 8,197 readable cases
per decoder, or 1,064,970 total evaluations. --quick uses one pattern and retains
all readable cases: 147,466 total evaluations across both decoders. This includes
45,815 catalogue encodings plus explicit ILLEGAL 0x4AFC (45,816 combined), and
19,720 other words including reserved forms and line-A/F. Illegal encodings must
raise the expected exception; they are not skipped. The complete strict run on
2026-10-31 passed all 1,064,970 evaluations through both decoders, with zero
failures or crashes. See COVERAGE.txt for the measured validation layers.

The independent core is Musashi, https://github.com/kstenerud/Musashi
Pinned commit: 313ebf1bd9f4d0d93341eb5ce21fd8a119e9dbdd
reference.lock.json checks source bytes and Git blob SHA before compilation.
The MIT core and bundled SoftFloat retain their licenses. They are downloaded to
ignored build data and linked only into reference_worker, never production.

The oracle is checked against every readable case. Exactly three pre-existing
divide-state discrepancies remain enumerated in reference-limitations.json;
any different disagreement fails the oracle validation. Correct readable
expectations are retained. Specific known oracle bugs are corrected in the
independent wrapper using documented hardware behavior and unchanged MAME
vectors: timing tables, invalid BCD digits, address-fault staging, LINK A7,
CHK trap timing, dummy reads and later-CPU MOVE16 dispatch. See
ORACLE-CORRECTIONS.txt for the exact corrections and evidence. No production
CPU outputs are given to the reference worker.

Musashi does not supply operand-accurate MUL/DIV timing, so those differential
cycle totals are unchecked. The independent MAME vectors still assert them.
Undefined BCD/divide/CHK flags are masked according to the manuals. All three
layers assert CHK's defined N on a taken bounds trap, including its saved SR.
Only C/V/Z are omitted on that trap; successful CHK leaves NZVC undefined.
Other defined frame fields remain checked. Corpus instruction
semantics are stepped before a subsequent trace boundary, while production and
readable sequence tests execute the real trace boundary.

Reports contain report.json and instructions.csv with source/expectation hashes,
counts, state/timing differences, failure examples and crash diagnostics. A
crashed case does not hide later inputs: workers restart with bounded batches.
CI runs the strict one-pattern complete-word command on Linux and Windows;
the eight-pattern command is available for deeper local validation.

Sanitizer checks
----------------

    cmake -S UnitTests -B build/cpu-sanitized -DCMAKE_BUILD_TYPE=Debug -DDRIVONIX_SANITIZERS=ON
    cmake --build build/cpu-sanitized --parallel 2
    ctest --test-dir build/cpu-sanitized --output-on-failure
    python UnitTests/conformance/complete.py --worker build/cpu-sanitized/vector_worker --specifications-only --profile sanitizers --report-dir build/specifications-sanitized

All seven CTest targets and all expanded specifications require zero failures
and zero sanitizer crashes. The final 16,394 readable evaluations passed strictly
under ASan/UBSan on 2026-10-31. The old sanitizer snapshot is historical evidence of
previous unsafe behavior, not permission to retain it. Passing these checks does
not prove that every possible input or production console path is sanitizer-safe.

Production Z80 specifications
----------------------------

The production backend uses the cycle-stepped floooh/chips Z80 through Z80/core.c,
shared by the console and z80_worker. Its wrapper handles the NMOS state/latches
and documented quirks exercised by the pinned corpus. Build the root project
with the Linux/Windows dependencies described in the main README:

    cmake -S . -B build/emulator -DCMAKE_BUILD_TYPE=Release
    cmake --build build/emulator --config Release --target z80_worker --parallel 2
    python UnitTests/conformance/z80.py --fetch --worker build/emulator/z80_worker --report-dir build/z80-report

On Windows use build/emulator/Release/z80_worker.exe. The dataset download is
about 1.3 GB. --group selects exact stems, for example --group "dd cb __ 46".
The full strict run on 2026-10-31 executed and passed 1,604,000 cases across 1,604
instruction/prefix groups, with no failures. This is execution of the real shared
backend, not schema validation of a corpus without a CPU.

Source: https://github.com/SingleStepTests/z80
Pinned commit: ebe1875d48f374bcfd4b505d8eb8ee751568b5f7
z80.lock.json pins bytes/blob hashes and z80-license.txt retains the MIT notice.

The worker receives initial state/RAM, read-port inputs and observed addresses,
never expected final state or timing. Comparison includes the architectural and
undocumented register/latch state, changed RAM, I/O transactions and total
instruction T-states for base, CB, ED, DD/FD and indexed-CB forms. The production
worker does not emit per-pin traces, so --pins is not a passing coverage mode.
Interrupt/bus integration is tested separately by the root sound_z80_hardware
checks; the single-step corpus is not an exhaustive interrupt-sequence proof.
See ../../Z80/README.txt for implementation and sound integration details.

Remaining hardware boundaries
-----------------------------

The CPU fixtures do not certify electrical pins, byte strobes, wait states,
bus arbitration, externally injected bus errors/double-fault halt, or vectored/
spurious interrupt acknowledge. They observe address errors, autovectored IRQs,
RESET callback delivery and selected prefetch consequences; the final internal
prefetch queue is not compared. Z80 pin waveforms are not emitted by its worker.
Console tests separately exercise device mapping, clocks, DMA, rendering, sound,
saves and input. Booting a diagnostic ROM and passing CPU vectors do not establish
full game compatibility, perfect raster timing or measured commercial-game
performance. See COVERAGE.txt for current measured results.
