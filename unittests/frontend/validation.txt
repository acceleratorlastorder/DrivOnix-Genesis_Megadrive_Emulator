Base-console integration validation (2026-10-31)
================================================

These checks execute the production console modules. They supplement the
isolated MC68000 specifications documented in unittests/readme.txt; passing
instruction tests alone does not establish complete console compatibility.

Reproduce the offline console tests from the repository root:

  cmake -S . -B build/linux -DCMAKE_BUILD_TYPE=Release
  cmake --build build/linux --parallel 2
  ctest --test-dir build/linux --output-on-failure

  cmake -S . -B build/console-sanitized -DCMAKE_BUILD_TYPE=Debug -DDRIVONIX_SANITIZERS=ON
  cmake --build build/console-sanitized --parallel 2
  ctest --test-dir build/console-sanitized --output-on-failure

Observed layers
---------------

* console_hardware: real 68000 bus routes, 64 KiB RAM mirrors, I/O and Z80 byte
  lanes, hardware region/version bits and master clocks, VDP floating status
  bits, FIFO destination capture, timed DMA/stalls/fill, six-button handshakes,
  NTSC/PAL frame periods, simple rendered scenes, SRAM and cartridge banks.
* vdp_hardware: fixed pixel expectations for planes, window replacement and
  alignment, flips, scroll columns, sprite order/priority/collision, transparent
  colors, shadow/highlight, woven interlace fields, H32/H40 counters, HV freeze,
  blanking edges and interrupt-latch priority. Headless and GUI builds share
  the renderer; see ym7101/readme.txt for the precise timing boundaries.
* sound_z80_hardware and z80_bus_hardware: real Z80 execution, RAM/bank/reset/
  bus ownership and interrupts; VDP/PSG aliases and byte lanes; continuation
  after nested FIFO waits; exact audio clocks across host scheduling slices;
  PSG tone/mute, YM2612 timer/busy/DAC/stereo, PAL/NTSC sample totals.
* rom_loader and frontend_cli: BIN/MD/GEN/SMD loading, buffer/bounds failures,
  odd-size checksums without ROM mutation, hardware-region parsing, startup
  errors and asset lookup from another working directory.
* eeprom_hardware: serial addressing, ACK/NACK, repeated starts, page wrap,
  sequential reads and busy intervals across every supported geometry.
* vendor_sources: all 14 pinned z80/audio/parser source and license hashes.

The separate strict Z80 worker passed all 1,604,000 pinned instruction cases.
It compares register/RAM/I/O results and total T-states, not per-pin waveforms.
The external CPU corpus is fetched only when explicitly requested; ordinary
console CTest uses generated fixtures and needs no external game ROM.
The final local Release and ASan/UBSan builds passed all nine console CTest
targets; installed CLI lookup and packaged executable permissions also passed.

Persistence regressions
-----------------------

cartridge_persistence drives Cartridge through the real Genesis byte/word bus.
It verifies original loader/ROM bytes, odd/even/two-lane SRAM file packing,
enable/protection and overlapping ROM, all eight bank windows, and Sega/EA/
Acclaim/Codemasters EEPROM wiring, file geometry and same-file dirty reload.
Both cartridge-insertion overloads retain regional EEPROM busy timing after
Init/reload. Tests use a unique directory beneath the supplied build fixture
directory and remove their own files; they never access a user's saves.

Linux test-only linker wrappers force a seven-byte partial write followed by
ENOSPC, and atomic rename EACCES. Existing canonical saves remain unchanged,
temporary files are removed, changed SRAM/EEPROM memory survives, and retry
persists the new bytes. Portable filesystem obstructions exercise native
temporary-file creation and replacement failures on Linux and Windows. POSIX
directory permissions additionally verify retry after restoring writability.
No production fault-injection hook or actual disk-filling operation is used.

Existing unreadable SRAM/EEPROM saves must raise errors, rather than become
fresh FF memory. POSIX permission denial and a Windows exclusive read lock
exercise this rule. Rejected candidates preserve the old cartridge, SRAM
protection, save path and in-flight EEPROM transaction. Relinking pre-fix
cartridge.cpp from dff66f6 against the new test fails with "Unreadable existing
save was treated as a missing save"; the correction passes normal and
ASan/UBSan runs. Candidate ROM/save bytes are validated before committing state.

Failures before atomic replacement preserve the old file. Directory fsync is
after replacement: a reported directory-sync error may leave the new file in
place, with dirty memory retained for retry. Power-cut durability, fsync failure
injection and concurrent emulator processes writing the same save are not
certified by these tests. Save states are not implemented.

Generated graphical checks and CI
---------------------------------

  xvfb-run -a -s '-screen 0 1280x1024x24' python3 unittests/frontend/test_linux_gui.py --emulator build/linux/drivonix
  xvfb-run -a -s '-screen 0 1280x1024x24' python3 unittests/frontend/test_linux_regions.py --emulator build/linux/drivonix

The generated original cartridge checks native GTK selection/cancellation,
paths with spaces, BIOS rendering/handoff, red output, Start-driven green
output and clean exit. The region variant checks the cartridge-visible version
bits after the real BIOS/main handoff for Japan, European mask "8", and "JUE".
These are real rendered-window assertions, not mocked frontend responses.

emulator-build.yml runs console CTest on Linux and MSVC x64 Windows, installed
layout checks on both, full Z80 vectors and Xvfb GUI checks on Linux, and Linux
ASan/UBSan console tests. Windows builds pinned native SFML/CSFML, including
audio DLLs and licenses. GNU save fault wrappers are Linux-only; Windows runs
the native filesystem-obstruction/read-lock tests. CPU CI separately runs both
68000 decoders, sampled external vectors, every opcode word in the quick
independent sweep, and Linux sanitizers. Workflow configuration describes the
required scope; a particular revision still needs its own green CI run.

Diagnostic and performance boundaries
-------------------------------------

The author-provided MegaDrive/Genesis 240p Test Suite 1.32 was obtained from
https://artemiourbina.itch.io/240p-test-suite and is not redistributed here.
The tested 262,144-byte normal ROM has SHA-256:
  fe448a879eda25daffa1548385aff464d5373c687db0cccf18f071c31d0976c7

Place a separately obtained matching image under build/fixtures to reproduce:

  ./build/linux/console_runner build/fixtures/240p-test-suite-1.32.bin 600
  ./build/linux/console_runner bios/drivonix.bios 1500 --bios --z80

Generate the independent controlled active-z80/PSG workload:

python3 - <<'PY'
import sys
from pathlib import Path
sys.path.insert(0, 'unittests/frontend')
from test_linux_gui import cartridge
Path('build/fixtures').mkdir(parents=True, exist_ok=True)
Path('build/fixtures/generated-input.bin').write_bytes(cartridge())
PY
  ./build/linux/console_runner build/fixtures/generated-input.bin 600 --z80

Measured Release samples on a shared AMD Ryzen 9 3900X host:

  Workload               Frames  Emulated s  Wall s   Wall/emu  Emu/wall
  240p normal cartridge     600   10.012894   2.57050   0.2567    3.8953
  BIOS to handoff           618   10.313281   2.29316   0.2224    4.4974
  Generated ROM + --z80     600   10.012894   2.62351   0.2620    3.8166

Emulated seconds use reported master clocks / 53,693,175 (NTSC). The controlled
run records 35,841,603 executed Z80 T-states, 480,618 stereo audio frames and
the expected red framebuffer center. The 240p run records 480,618 audio frames
and a final framebuffer dump; the BIOS reports handoff at frame 617 (618 total).
These are individual throughput observations, without repeated-run statistics.

The headless runner uses production CPU/video/audio scheduling and reports
emulated clocks, wall time and generated audio samples. It omits host audio
playback, display presentation and real-time pacing. Completing 600 diagnostic
frames is a boot/execution observation; it does not mean every diagnostic menu,
controller operation or expected video/audio result was automatically checked.
BIOS startup can reset/replace Z80 code, so --bios --z80 alone does not prove
sustained active-Z80 throughput.

Rendering remains scanline based. Arbitrary mid-line fetch effects, complete
sprite-attribute caching, interlace half-line details, physical bus arbitration
and pin waveforms remain bounded; see the VDP/Z80 module notes. Unknown save
boards, J-Cart, Sega CD, 32X, SVP and other special hardware are not covered.
No commercial-game compatibility matrix or universal minimum-host performance
guarantee follows from these tests or a single headless benchmark.
